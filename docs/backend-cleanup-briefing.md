## Track A — Linux bundle slimming

The CPU Engine is **1.8 GB** and nothing prunes it. There is no strip or prune
step anywhere in `scripts/` (the only `strip` match is
`tar --strip-components`, which is unrelated).

Measured on `dist/StemLab-0.9.9-Linux-cpu/Engine`:

| item | size |
|---|---|
| `__pycache__` directories | 268 MB |
| bundled test suites | 228 MB |
| `.so` files, unstripped | 1069 MB across 316 files; ~22% recoverable ≈ 235 MB |
| Tcl/Tk | 5 MB |

This matters beyond disk: `.github/workflows/release.yml` splits any bundle over
1900 MiB into `.partNN` files with sidecars. Removing ~700 MB may drop several
flavours back under that limit and delete a whole class of release complexity.

Add a prune step at the end of the Engine build in
`scripts/linux/install_backend.sh`. Requirements:

1. **Strip shared objects** — `strip --strip-unneeded` on `*.so*`. Do it in a
   loop that tolerates failure per file; some are already stripped and some are
   not ELF. Never `strip` (without `--strip-unneeded`) a shared library.
2. **Remove bundled test suites** — but be careful. `numpy/testing` is a public
   API that packages import at runtime; `sklearn/**/tests` and `scipy/**/tests`
   are not. Match on `tests` directories nested inside packages, exclude any
   path segment named exactly `testing`, and verify by importing afterwards.
3. **Tcl/Tk and `tkinter`** — only if nothing imports it. Check first:
   `grep -rl "import tkinter\|from tkinter" src/ scripts/`.
4. **`__pycache__` — measure before deciding.** This is *not* free: dropping the
   bytecode means every module is recompiled on first import, and if the install
   directory is not writable it is recompiled on *every* run. Time
   `python -c "import stemlab.pipeline"` with and without, on a cold page cache,
   and only remove it if the cost is small. If it is not, leave it and say so in
   the PR — 268 MB is not worth a visibly slower first launch. An alternative
   worth pricing: keep `__pycache__` and drop the `.py` sources, which is
   smaller still, but breaks tracebacks and any package that reads its own
   source. Do not do that without asking.

**Verification is the deliverable here, not the size number.** After pruning,
the Engine must still run a real separation end to end. Build a bundle, run a
short file through `python -m stemlab.cli` (or the same entry the plugin uses),
and confirm six stems come out. A bundle that is 700 MB smaller and cannot
separate is a regression, and the size figure in the PR body is worthless
without that check beside it.

Report actual before/after sizes per flavour if you can build more than one.

## Track C — Resample to 44.1 kHz for BS-RoFormer

BS-RoFormer is trained at 44.1 kHz but receives audio at whatever rate the
source is:

- `bs_roformer/inference.py:92` — `mix, sr = sf.read(path)`, no resample.
- `bs_roformer/inference.py:116` — writes back at the same `sr`.
- `src/stemlab/bs_roformer_cli.py` is only a launcher into that entry point.
- Nothing in StemLab resamples first. `audio.py`'s `target_sr` is used solely at
  `hybrid.py:173`, to align demucs output to the roformer rate *after the fact*.

Evidence for 44.1 kHz: `bs_roformer.py` documents `stft_hop_length: 512` as
"10ms at 44100Hz", and the config's `chunk_size: 588800` is 13.35 s at 44.1 kHz.
At 48 kHz every band-split boundary lands 8.8% high — about 1.5 semitones — so
the model's learned frequency priors are misaligned. Output pitch and duration
are unaffected; the damage is degraded separation and extra bleed.

**Fix it in our code, not theirs.** `inference.py` lives in `site-packages` and
is pip-installed; patching it there is fragile and would be undone by any
reinstall. Instead, in the StemLab wrapper: if the input is not 44100, resample
to 44100 into a temporary file, run the model on that, then resample the stems
back to the source rate before they are returned. Use `soxr` — already a
dependency, see `beat_tracking.py:510` — not `resample_poly`, for quality.

Requirements:

- A 44.1 kHz input must take a byte-identical path to today. Prove it with a
  test, not by inspection.
- Round-tripping must preserve length exactly; off-by-a-few-samples here would
  desync stems against the session.
- Handle the hybrid path too: with RoFormer corrected, re-check that
  `hybrid.py:173` still aligns rates correctly rather than double-resampling.
- Add tests to `tests/`. The existing regression harness
  (`src/stemlab/regression/`) is the right tool for asserting the stems still
  reconstruct the mixture.

Note in the PR that this changes output for 48 kHz sources — that is the point,
but it should be stated rather than discovered.

## Track D — Measurements (produces a report, changes no behaviour)

Three numbers nobody has. Run them, write the results into the PR description of
a docs-only change or into an issue; do not act on them.

1. **How much does the 48 kHz bug actually cost?** Take a 44.1 kHz track.
   Separate it normally. Upsample it to 48 kHz, separate again, downsample the
   stems back to 44.1 kHz. Compare with
   `PYTHONPATH=src python -m stemlab.regression`. That quantifies what 48 kHz
   users lose today and tells the owner whether Track C is urgent or cosmetic.
2. **`DEMUCS_OVERLAP = 0.10` vs upstream's 0.25** (`demucs_backend.py:26`).
   This is on `main` and ships to every user, not a local experiment. It came
   in with commit `c818817`, whose comment asserts that 0.10 "keeps the window
   seams inaudible while dropping that redundant compute". That claim carries
   no measurement: the same commit verified its other changes numerically
   (fusion deltas at 3e-8, refined stems within 1.5e-8 per sample), and the
   overlap change alone was reasoned rather than tested. So we are shipping a
   quality-for-speed trade whose quality side was never checked. Report both
   time and harness metrics for 0.10 and 0.25.
3. **RoFormer `num_overlap: 2` vs `1`.** 50% chunk overlap doubles compute.
   Report the same pair.

For every one of these, pass `--shifts 0` to demucs. Its default of 1 applies an
unseeded random offset, and two runs of the *same* configuration disagree about
as much as two different configurations do — enough to produce a completely
fictitious result. This is not hypothetical; it already happened once during the
demucs-rs evaluation and cost a day.

Use real music, not the synthetic corpus in `regression/corpus.py`. That corpus
is explicitly documented as not a quality benchmark, and on out-of-distribution
material both engines emit near-silence, which makes every metric meaningless.

## Out of scope — do not do these

These need the owner's decision and are covered in a separate briefing.

- **`--shifts` non-determinism.** Real bug, but the fix has three options with
  different sound: seed the RNG, pass `--shifts 0`, or leave and document.
- **fp16 on CUDA vs fp32 on CPU** (`bs_roformer/utils.py:79`,
  `torch.cuda.amp.autocast()`). Same input gives different quality per device.
  The call is inside third-party `site-packages`, so any fix means patching at
  install time or going upstream. Both the behaviour and the mechanism need a
  decision.
- **The BSRoformer.cpp / ggml spike** (task #53). Whether to spend anything here
  at all is an open question after demucs-rs was rejected on measurement.
- **Python 3.13.** `audioread/rawread.py` imports `audioop` and `sunau`, both
  removed in 3.13. Harmless on the pinned 3.11, but it blocks an interpreter
  bump. Strategy call, not a fix.
